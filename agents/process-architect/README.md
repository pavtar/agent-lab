# process-architect

Архитектор бизнес-процессов: помогает руководителю описывать, анализировать и проектировать процессы Uplab через BPM-подход Беккера и Value Stream Mapping Ротера.

## Задача

Сделать процессы Uplab видимыми и управляемыми: понять, как процесс работает сейчас, где теряется ценность, и каким должно быть следующее достижимое состояние с метриками, рисками и пилотом.

## Чем отличается от business-system-analyst

`business-system-analyst` отвечает за требования: BRD, ТЗ, user stories, постановки задач.

`process-architect` отвечает за процессы и потоки ценности: карты, метрики, потери, целевое состояние, план перехода.

Если по итогам работы `process-architect` нужно написать ТЗ для ИТ, дальше работу подхватывает `business-system-analyst`.

## Сценарии

- `process_assistant` — навигатор по методологии: какой подход выбрать и какой сценарий запустить.
- `process_assessment` — короткая диагностика процесса перед моделированием.
- `as_is_map` — карта "как есть" по BPM-подходу Беккера.
- `value_stream_map` — карта потока ценности по Ротеру.
- `to_be_design` — целевое состояние процесса с пилотом и рисками.

## Быстрый запуск в Cursor Agent

Откройте новый чат Cursor Agent и вставьте:

```text
Работай как агент process-architect.
Используй инструкции из agents/process-architect/prompt.md.
Сценарий: process_assistant.

Мой вопрос:
Хочу разобраться, какой подход выбрать для процесса согласования договоров.
```

Для другого режима замените сценарий на `process_assessment`, `as_is_map`, `value_stream_map` или `to_be_design`.

## Когда нужен SDK

Для первой версии SDK не нужен: работа интерактивная, агент запускается вручную через Cursor Agent.

SDK понадобится позже, если карты процессов нужно регулярно собирать по шаблону, сохранять в Obsidian с историей версий или генерировать сравнение текущего и целевого состояния.

## Первый результат

Один из артефактов в зависимости от сценария:

- короткая диагностика процесса перед моделированием;
- Markdown-карта процесса "как есть";
- Markdown-описание потока ценности;
- Markdown-описание целевого состояния с пилотом;
- навигация по методологии и рекомендация следующего сценария.

## Входные данные

- Название и контекст процесса.
- Цель моделирования и пользователь карты.
- Известные факты, метрики, наблюдения.
- Список участников и систем.
- Ограничения: сроки, бюджет, ИТ, регулирование.

## Выход

Markdown-документ в чате Cursor Agent. Если результат важен для управления, его сохраняют в `Company OS/Run Logs/` или в проектную папку.
