# 08. Разбор бизнес-проблемы через Toyota Kata

## Назначение

`problem_improvement` помогает руководителю разобрать конкретную бизнес-проблему без преждевременного перехода к готовым решениям. Результат сценария — Problem Improvement Canvas: challenge, current condition, target condition, obstacles и next experiment.

## Когда использовать

Сценарий подходит, если:

- есть важная бизнес-проблема, но путь решения не очевиден;
- команда спорит о решениях, не согласовав факты;
- нужно выбрать первое препятствие и безопасный эксперимент;
- проблема связана с процессом, который можно наблюдать;
- можно получить факты, метрики или примеры текущего состояния.

Сценарий не нужен, если решение уже известно и осталось только выполнить план. Тогда это обычное project management, а не Toyota Kata.

## Входные вопросы

Перед разбором агент уточняет:

1. Какую проблему разбираем?
2. Какой процесс или участок работы затронут?
3. Почему это важно для бизнеса?
4. Какие факты уже есть?
5. Как сейчас выглядит процесс?
6. Какой ближайший горизонт улучшения реалистичен?
7. Кто владелец процесса и кто будет проводить эксперимент?

Если данных мало, агент не должен придумывать current condition. Он фиксирует неизвестные зоны и предлагает первый шаг наблюдения.

## Проблема или готовый проект

Признаки бизнес-проблемы для Toyota Kata:

- неясно, почему процесс работает не так;
- неясно, какой следующий шаг сработает;
- есть несколько гипотез;
- нужны наблюдения и эксперименты;
- результат зависит от поведения людей или процесса.

Признаки готового проекта:

- решение уже выбрано;
- есть понятный список задач;
- нет существенной неопределённости;
- успех зависит в основном от исполнения плана.

Если пользователь пришёл с готовым решением, агент возвращает его к вопросу: "Какое состояние мы хотим получить и что мы знаем о текущем состоянии?"

## Challenge

Challenge — направление или вызов, который объясняет, зачем мы вообще улучшаем процесс.

Хороший challenge:

- связан с бизнес-целью;
- задаёт направление, но не диктует решение;
- достаточно широкий, чтобы иметь смысл;
- достаточно конкретный, чтобы выбрать первый процесс для работы.

Пример:

```text
Сократить потери времени в подготовке коммерческих предложений, чтобы команда быстрее отвечала клиентам без ухудшения качества расчётов.
```

## Current condition

Current condition описывает фактическое состояние сейчас.

Нужно фиксировать:

- факты;
- метрики;
- наблюдения;
- примеры;
- частоту проблемы;
- где данные отсутствуют.

Не нужно писать:

- обвинения;
- интерпретации без фактов;
- решения;
- общие формулировки вроде "процесс плохой".

## Target condition

Target condition — ближайшее целевое состояние. Это не финальная мечта и не список задач.

Хорошее target condition:

- имеет дату или горизонт;
- описывает, как должен работать процесс;
- содержит критерии проверки;
- достижимо через эксперименты;
- не содержит готового решения.

Плохо:

```text
Внедрить новый регламент согласования.
```

Лучше:

```text
К 30 июня все КП по типовым проектам проходят согласование за 2 рабочих дня, а статус и причина задержки видны владельцу процесса в день возникновения задержки.
```

## Obstacles

Список препятствий отвечает на вопрос: что мешает достичь target condition?

Правила:

- собрать несколько препятствий;
- не решать все сразу;
- выбрать одно препятствие в работу;
- объяснить, почему именно оно первое;
- если препятствие слишком большое, разбить его.

## One obstacle now

В каждый момент времени в работе одно препятствие. Это защищает сценарий от расползания в большой список задач.

Выбор первого препятствия должен учитывать:

- влияние на target condition;
- возможность проверить за короткий цикл;
- доступность данных;
- способность владельца процесса реально действовать.

## Next experiment

Следующий эксперимент формулируется как проверяемый шаг.

Минимальная структура:

| Поле | Содержание |
| --- | --- |
| Гипотеза | Если ___, то ___ |
| Шаг | Что сделаем |
| Ожидание | Что ожидаем увидеть |
| Проверка | Как поймём, что произошло |
| Срок | Когда посмотрим результат |

Эксперимент должен быть маленьким. Если он занимает месяц и требует многих команд, это уже проект, а не следующий шаг Kata.

## Формат результата агента

Агент `toyota-kata-coach` в сценарии `problem_improvement` должен выдать Markdown-документ:

1. Краткое описание бизнес-проблемы.
2. Challenge или направление.
3. Current condition: факты, метрики, наблюдения, неизвестные зоны.
4. Target condition: состояние на ближайший горизонт.
5. Obstacles: список препятствий.
6. One obstacle now: одно препятствие в работе.
7. Next experiment: гипотеза, шаг, ожидаемый результат, срок проверки.
8. Что нужно узнать до следующего цикла.
9. Риски: где мы могли перепрыгнуть к решению.

## Критерии качества

- Проблема привязана к реальному процессу.
- Current condition описан фактами.
- Target condition описывает состояние, а не решение.
- Есть список препятствий.
- Выбрано одно препятствие в работу.
- Next experiment содержит ожидание и срок проверки.
- Агент явно фиксирует неизвестные зоны.
- Агент не выдаёт готовое решение вместо эксперимента.
